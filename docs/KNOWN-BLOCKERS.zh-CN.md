[English](KNOWN-BLOCKERS.md) | [简体中文](KNOWN-BLOCKERS.zh-CN.md)

本页记录用当前工具链**无法**闭环的内容，免得贡献者再花几个小时重新发现。下面全部在日版构建
（`SLPS_258.19`，载荷 `sha1:7cc42d275750600d…`）上用 `ee-gcc 3.2-ee-040921` 实测。

> 范围：**主**口径只统计**重建的 C**。字节一致的汇编转录是另一个口径 —— 见

## 1. 工具陷阱（会产生错误结果）

| 陷阱 | 会发生什么 | 应该怎么做 |
| --- | --- | --- |
| 对 ee-gcc 对象用 `objcopy --only-section=.text` | 在这种旧 ELF 上失败，并且**两侧都静默返回空字节** —— 天真的字节比较随后会报告「一致」。 | 用 `objdump -s -j .text` 比较十六进制。 |
| 用 `objdump -d` 做精确字节比较 | 会**静默跳过**它无法解码的指令（在一个向量密集的函数里观察到 18 条）。 | 比较原始节字节，不要比较反汇编。 |
| `ee-as` 配 `.set noreorder` + `.word` | 多产生 **20 字节**填充。 | 用默认的 reorder 模式（但注意它会在分支延迟槽插入 `nop`）。 |
| 信任记录下来的 `-O*` 标志 | 获胜档位常常不是记录的那个（`-O3` 和 `-O2 -fno-optimize-sibling-calls` 都出现过；记录写 `-O1` 的有时需要 `-O3`）。 | 总是扫 `-O1 / -O2 / -O3 / -Os`，保留能达到 100 的那个。 |
| 只比较 objdiff 百分比 | 字节一致的 `.text`，若**重定位目标符号名**不同，分数仍 < 100。 | 检查重定位符号，而不只是字节。 |

## 2. 不可达的代码生成形态

有些零售指令序列无法由普通 C 配这个编译器产生，因为 GCC 会先把源码折叠掉。两个已确认的例子：

- **`lh` + `sltiu`**：零售代码加载一个 `short`（有符号）却按**无符号**比较，例如
  `lh t7,0x20(a0)` 后跟 `sltiu t7,t7,0x2`。源码里写 `(unsigned)short_var < 2` 会让
  GCC 3.2 折叠回 `slti`，所以这一对不可达。试过五种源码变体，全部停在同一个差异。
- **`beqzl`（branch-likely）**：只有掌握分支预测信息时 GCC 才会生成 branch-likely 形态。
  单靠 `__builtin_expect` 而不加 `-fbranch-probabilities` 不会触发。

**停止条件**：如果只剩一个差异且属于这些形态，接受它，继续前进。

## 3. 寄存器分配的残余

95–100% 区间的函数常常只差在**寄存器分配**（操作数上的 `arg_diff` /
`DIFF_ARG_MISMATCH`）或函数序言（prologue）的指令顺序（`DIFF_INSERT`）。

- 重写源码重新排列求值顺序（局部临时变量、重排 `+` 链）在所有实测案例中**都没有**改变分数。
- 本地 permuter 也用改进后的 93.75% 源码作种子喂过，返回 0 命中。

**停止条件**：三个源码变体都没有改变分数 ⇒ 残余是分配器行为；停止。

## 4. 已经枯竭的渠道

| 渠道 | 试过的规模 | 结果 |
| --- | ---: | --- |
| 在 ≥ 80% 接近线的分段上跑本地 permuter | 361 个样本 | 9 命中（**2.5%**），且最后连续三批都是 0 命中 |
| LLM 生成的草稿（Cohere / Codestral） | 24 个样本 | 0 转换（Cohere 2/12 编译通过，Codestral 10/12 编译通过，没有一个匹配） |
| 基于 `objcopy` 的字节比较 | — | 见 §1：完全不可用 |

## 5. 仍然有效的做法

- 接近项上的**类型 / 结构恢复**：声明一个结构体，大小等于零售的 **stride**，把成员放在零售的
  **字段偏移**上，再按索引访问 —— 3/3 成功。修正表的**元素类型**（例如 `unsigned int` →
  `char[]`）能纠正 4 倍的 stride 错误。
- **有符号性扫描**：零售方向相反的第一个分支上出现 `DIFF_REPLACE`，意味着草拟的全局变量被
  声明成 `unsigned`，而零售代码按有符号处理。修正声明在每个试过的案例上都有改善（2/2）。
- **`diff_kind` 定位**：objdiff 的 JSON 带有 `instructions[].diff_kind`，这是枚举剩余精确差异
  的可靠方法，不必写字节解析器。

## 6. 报告阻塞项

如果遇到新情况，请开 issue 并附上：

1. 符号、它在零售里的尺寸，以及当前 objdiff 分数；
2. 精确的 `diff_kind` 列表（或反汇编对）；
3. 你试过的源码变体及各自分数。

这些足够别人复现 —— 也许还能找到可行的形态。

## 7. 发布前核验报告

发布的数字必须来自**合并提交上一次绿色的 `matching-gate` 运行**。两项检查把关，任何一项不符
都意味着**不要发布**：

1. `report_provenance.json` → `source_commit` 等于你正在发布的合并提交；
2. `payload_check.ok == true`（且 `baseline_sha1 == mixed_sha1 == 7cc42d27…`）。

两个陷阱会产生**看起来合理但错误**的产物：

- 用**空的 run id** 跑 `gh run download` 会静默回退到「最新一次运行」—— 而 pull-request 运行
  携带的是**合成的合并引用**（`refs/pull/N/merge`），其 SHA 不是 `main` 上的提交。要从合并提交
  的 **push** 事件解析 run id，为空时中止。
- 报告任务若看不到基线二进制，会报告 `payload_check.ok = false` 且 `baseline_sha1: null` ——
  即使其它数字看起来都对，该产物也不可发布。
